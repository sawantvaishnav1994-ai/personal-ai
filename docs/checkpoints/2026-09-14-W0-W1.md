## Root cause repaired

The production `personal-ai-runtime` Railway service has no persistent volume. The application previously defaulted hosted state to the container filesystem and could therefore silently initialize SQLite databases and owner data on ephemeral storage.

The new startup guard validates hosted storage before `build_runtime()` opens production stores. A hosted runtime now requires:

1. `PERSONAL_AI_DATA_DIR` to resolve beneath `PERSONAL_AI_DURABLE_ROOT` (default `/data`).
2. A real non-root Linux mount to contain that data directory.
3. A successful write + flush + `fsync` + read-back storage probe.

Failure raises `StorageUnavailable` and prevents the privileged runtime from starting on unproven ephemeral storage. Local/desktop operation remains unaffected.

## Read-only security inspection completed in parallel

Initial W2 findings:

1. Approval tickets are process-memory only in `security/approvals.py`.
2. Paused executor continuations are process-memory only in `agent/executor.py`.
3. Current tickets bind execution/tool/parameter hash but not the full owner/device/session/security-epoch/destination/classification scope.
4. Cloud sessions are durable and nonce-protected, but `SecureCloudRelay.command()` currently invokes the executor without forwarding the authenticated device/session identity.
5. Cloud approval redemption uses the approval ID without binding the approving cloud session to the original request.
6. A handler return without exception is still treated as successful execution; a generic verification contract/rollback metadata layer is not yet enforced.
